# طريقة عمل الفريق

هذا هو المصدر الوحيد لتعليمات العمل لكل مطور ومبرمج ووكيل. يقرأ كاملاً قبل كل مهمة أو استئنافها. AGENTS.md وCONTRIBUTING.md في جذر المستودع نقطتا توجيه إلى هذا الدليل؛ تعدل التعليمات هنا فقط. تعليمات المستخدم الصريحة الخاصة بالمهمة مقدمة عند التعارض، ولا يتحول استثناء لمهمة واحدة إلى قاعدة دائمة.

## مفاهيم أساسية

- clone: تنزيل المستودع أول مرة فقط.
- fetch: جلب معلومات الفروع البعيدة دون دمجها في ملفاتك.
- pull: جلب التحديثات ودمجها في الفرع الحالي؛ نستخدم --ff-only كي لا ننشئ دمجاً غير مقصود.
- commit: حفظ خطوة متماسكة محلياً، لا يرفعها إلى GitHub.
- push: رفع commits إلى فرعك البعيد، ولا يدمجها تلقائياً إلى main.
- Pull Request: طلب مراجعة ودمج فرع المهمة إلى main.

المجلدات تخصص المسؤوليات؛ الفروع تعزل التعديلات. كل عضو لديه نسخة المشروع كاملة. رفع التحديثات لا يحدث نسخ أجهزة الآخرين تلقائياً.

## عند البداية أو الاستئناف

افحص قبل التعديل:

<div dir="ltr" align="left">

```sh
git status --short
git branch --show-current
git remote -v
git fetch origin
```

</div>


يجب أن يكون origin مستودع elith-bot/graduation-project. إذا كان مختلفاً، تحقق قبل أي رفع. اقرأ [README](../README.md) و[الهيكلية](ARCHITECTURE.md) و[مسؤوليات الفريق](TEAM.md) وREADME للجزء المتأثر و[عقود البيانات](../contracts/README.md).

إذا كانت هناك ملفات معدلة، لا تسحب أو تبدل الفرع عشوائياً: ميز عملك من عمل الآخرين، واحفظ عملك المتماسك بفرعه فقط. لا تحذف أو تستبدل ملفات لتجعل مساحة العمل نظيفة. إذا فشل fetch، حل مشكلة الوصول قبل بناء تعديل على أساس قديم قدر الإمكان، واذكر أي عائق.

## الدورة اليومية

1. حدث main المحلي، وأنشئ فرعاً جديداً لكل مهمة.
2. نفذ التغيير وجربه محلياً. كل عضو لديه نسخة كاملة من المستودع، ويعمل عادة ضمن الجزء المسؤول عنه.
3. أضف الملفات المقصودة فقط إلى commit وارفع فرع المهمة.
4. افتح Pull Request إلى main يذكر المشكلة والتغيير وطريقة التحقق.
5. اطلب مراجعة عضو آخر؛ وعند تعديل جزء آخر اطلب مراجعة مسؤوله.
6. عالج الملاحظات وتأكد من نجاح الفحوصات المتاحة قبل الدمج.

مثال بعد تنزيل المستودع أول مرة:

<div dir="ltr" align="left">

```sh
git clone https://github.com/elith-bot/graduation-project.git
cd graduation-project
git switch main
git pull --ff-only origin main
git switch -c feature/incident-list
# نفذ التغيير، ثم أضف الملفات المقصودة واحفظها
git add frontend/README.md
git commit -m "Document incident list behavior"
git push -u origin feature/incident-list
```

</div>


استبدل أسماء الفرع والملفات بما يناسب المهمة. إذا كانت لديك تغييرات محلية، احفظها بفرعك قبل التبديل. الفرع للمهمة، وليس فرعاً دائماً منفصلاً لكل شخص. رفع فرع لا يرفع التغييرات إلى main تلقائياً.

## استكمال مهمة موجودة

تأكد أولاً أن طلبها لم يدمج أو يغلق، وأن مساحة العمل نظيفة، ثم:

<div dir="ltr" align="left">

```sh
git switch feature/incident-list
git pull --ff-only origin feature/incident-list
git merge origin/main
```

</div>


الأسماء أمثلة. إذا لم ينشأ فرع بعيد بعد، تجاوز pull لذلك الفرع. إذا تباعد فرعك عن نظيره البعيد، توقف وافحص الفروق ونسق مع المشاركين بدل force push. merge origin/main يجلب آخر main إلى فرع المهمة دون إعادة كتابة تاريخه؛ إذا ظهرت تعارضات افهم النسختين ونسق الحل ثم اختبر واحفظ الحل.

## مع كل خطوة تعديل مكتملة

لا يلزم commit لكل حفظ أو سطر. احفظ وارفع كل خطوة متماسكة قابلة للفهم والمراجعة، وقبل تسليم العمل أو نهاية الجلسة. إذا اضطررت لتسليم عمل غير مكتمل، وضح أنه WIP وافتح الطلب كمسودة؛ لا تدمجه بوصفه جاهزاً.

<div dir="ltr" align="left">

```sh
git diff
git diff --check
# شغل فحوصات الجزء المناسبة، ثم أضف الملفات المقصودة فقط
git add frontend/README.md
git diff --cached
git commit -m "Clarify frontend API usage"
git push
git status --short
git rev-parse HEAD
git ls-remote origin refs/heads/feature/incident-list
```

</div>


في أول رفع استخدم push -u origin مع اسم الفرع. قارن SHA المحلي بالبعيد عند التحقق من اكتمال الرفع. افحص أيضاً الملفات الجديدة لأنها لا تظهر في git diff قبل إضافتها. لا تستخدم git add . دون مراجعة كل الملفات؛ ولا ترفع تغييرات غير مرتبطة بالمهمة. إذا رفض push لأن الفرع البعيد تقدم، اجلب التغييرات وافحصها وادمجها مع عملك واختبر من جديد؛ لا تتجاوزها بالقوة.

إذا لم يحدث تغيير فلا تنشئ commit فارغاً. لا تسحب قبل كل ضغطة أو أثناء تغييرات غير محفوظة؛ المزامنة تكون قبل بدء أو استئناف المهمة، وقبل الرفع عند وجود تغييرات بعيدة، وقبل الدمج النهائي.

## طلب الدمج وما بعده

- افتح طلباً واحداً لكل مهمة مع بيان التغيير والأجزاء المتأثرة والفحوصات. commits التالية على نفس الفرع تظهر في الطلب نفسه.
- أعد المراجعة إذا تغيرت الملفات بعد الموافقة، خصوصاً العقود أو سلوك الجزء الذي تمت مراجعته.
- تحقق من قابلية الدمج وآخر تغييرات main والفحوصات المتاحة والموافقات المطلوبة قبل الدمج.
- الاستثناء الصريح من صاحب المشروع يسمح بتجاوز المراجعة للطلب المحدد فقط؛ لا يعتبر تصريحاً دائماً للطلبات اللاحقة.
- بعد الدمج، يحدث كل عضو main المحلي وهو نظيف:

<div dir="ltr" align="left">

```sh
git switch main
git pull --ff-only origin main
```

</div>


ابدأ المهمة التالية بفرع جديد من main المحدث؛ لا تواصل العمل بفرع طلب مدمج. لا تحذف فرعاً يحتوي عملاً غير مدمج، ولا تحذف فروع غيرك. إذا غابت صلاحية الرفع أو تعطل الاتصال، اذكر أن العمل محلي ولم يرفع بعد.

## التسليم المختصر

كل مطور أو وكيل يسلم: ما تغير، الملفات أو الأجزاء المتأثرة، ما تم فحصه ونتيجته، اسم الفرع وcommit، رابط الطلب، وحالته: محلي فقط / مرفوع بانتظار المراجعة / مدمج. تذكر المشكلات والأعمال المتبقية بوضوح.

## تعديل جزء شخص آخر

- تغيير صغير: يمكنك تنفيذه بفرعك ثم طلب مراجعة مسؤول الجزء قبل الدمج.
- تغيير كبير: افتح مهمة واتفق مع المسؤول على النطاق ومن ينفذه قبل البدء.
- تغيير عقد بيانات أو API: يلزم تنسيق ومراجعة أصحاب الأجزاء المنتجة والمستهلكة، وتحديث العقود والعينات.
- عند غياب المسؤول: يتولى عضو آخر التنفيذ ويراجعه عضو مطلع على الجزء؛ لا نوقف العمل بلا بديل.
- تجنب العمل المتزامن على الملفات نفسها. أعلن بالمهمة الملفات المشتركة التي ستعدلها.
- عند تعارض الدمج: نسق مع صاحب التغيير وافهم التعديلين؛ لا تستبدل عمله تلقائياً، ولا تستخدم force push على main.

## قواعد المراجعة

- لا نرفع مباشرة إلى main وفق اتفاق الفريق؛ يراجع عضو آخر كل طلب دمج.
- لا يُدمج طلب يغير البيانات المشتركة دون تحديث الوثائق والعينات المتأثرة.
- تكون الاختبارات مناسبة للسلوك المتغير، وتذكر نتيجة التحقق أو سبب عدم تشغيله.
- وثق الجزء الذي تكتبه بالتدريج لدعم البحث والمناقشة.
- ملفات الأسرار وبيانات الحوادث الحقيقية تبقى خارج المستودع العام؛ استخدم بيانات اصطناعية وملفات .env.example بلا قيم سرية.

هذه قواعد عمل موثقة، وليست حماية تقنية مفعلة. حماية main وفرض الموافقات عبر GitHub إعداد منفصل لم ينفذ ضمن تثبيت الهيكلية. صلاحية Write لا تقيد العضو بمجلد معين. يضاف CODEOWNERS بعد تثبيت توزيع الحسابات؛ لا نعتمد أسماء غير متفق عليها.
## قواعد تنفيذ مشتركة للمطورين والوكلاء

- ملفات Markdown العربية تستخدم غلاف HTML باتجاه rtl مع سطر فارغ بعد فتحه وقبل إغلاقه، وتستخدم كتل الكود والأوامر والرسوم غلافاً داخلياً باتجاه ltr ومحاذاة left. حافظ على الأغلفة عند التعديل وأضفها للوثائق الجديدة؛ لا تكررها فوق غلاف موجود. هذا توجيه عرض للقراء الذين يدعمون HTML، وقد تتجاهله بعض تطبيقات الهاتف. لا تغير ترتيب النص أو تضف محارف اتجاه مخفية لمعالجة العرض.

- التقنيات وحدود الأجزاء مرجعها docs/ARCHITECTURE.md: FastAPI وPython للباك إند، وHTML/CSS/JavaScript وfetch وJSON عبر /api/ للواجهة، ومن نفس الأصل في النسخة الأولى.
- لا تغير الحدود أو تضف إطاراً أو خدمة أو اعتماداً كبيراً دون توثيق السبب والاتفاق عليه.
- لا تعلن اكتمال ميزة أو تكامل اعتماداً على بيانات تجريبية وحدها. لا تختلق نتائج فحوصات أو تدع تشغيل اختبار لم ينفذ.
- لا تستخدم reset --hard أو git clean أو force push لمعالجة المزامنة، ولا تحذف فروعاً أو تغير إعدادات الحماية لتجاوز عائق. حافظ على عمل الآخرين ونسق عند غموض التعارض.
- لا ترفع محتويات .local/ أو .env أو المفاتيح أو سجلات الحوادث الحقيقية، ولا تعرض أسراراً في مخرجات الأدوات.
- قبل التسليم تحقق من حالة طلب الدمج ومن تطابق commit المحلي مع الفرع البعيد. إذا تعذر السحب أو الرفع، احتفظ بالعمل واذكر العائق بوضوح.
