# الهيكلية المعتمدة — الإصدار 3 (تصميم موحد)

هذه الوثيقة هي المصدر المعتمد لحدود أجزاء المنصة الموحدة. أسماء المجلدات تمثل الوظائف وتبقى ثابتة إذا تغير توزيع الأعضاء. السلوك المتسلسل مصدره [SYSTEM_FLOW.md](SYSTEM_FLOW.md).

## تدفق البيانات

Wazuh → integrations → backend → engine → backend → frontend

يحوّل التكامل الحدث إلى العقد المشترك. يتحقق backend منه ويحفظه، ويستدعي engine، ويحفظ الحوادث الناتجة ويعرضها عبر API. يختبر evaluation السيناريوهات والنتائج. هذا ترتيب منطقي مقترح؛ تفاصيل الاستدعاء والجدولة تُحسم قبل التنفيذ.

داخل engine: تجميع وربط وفرز أولي → checklist أدلة → تقييم تغطية من اختبارات وتبعيات → إعادة قرار التحقيق. وحدة صمود تحلل الخريطة وتقترح تحسينات، وتغذي نتائج الاختبار اللاحق تقييم التغطية. ML مؤجل ويبدأ عند إضافته بـShadow دون تغيير القرار القاعدي.

توحيد حقول Wazuh مسؤولية integrations، والتحقق من العقد ومنع إعادة إدخال نفس هوية المصدر مسؤولية backend. تجميع التنبيهات بقائمة العمل وربطها مسؤولية engine. البيانات الأصلية تبقى محفوظة ولا تفسر كل مجموعة مدمجة كتنبيهات خاطئة.

## حدود الأجزاء

| الجزء | يملك | لا يملك |
|---|---|---|
| backend | API، التحقق عند الاستقبال، ترحيلات قاعدة البيانات، التخزين، صلاحيات التطبيق | قواعد ربط الأحداث أو الاتصال المباشر بـWazuh |
| engine | الفرز والربط والأدلة والتغطية والتبعيات ومحاكاة الفشل وإعادة القرار والتوصيات | الواجهة أو قاعدة البيانات أو تعطيل المختبر مباشرة |
| frontend | العرض والبحث والتصفية والخط الزمني وعرض التقارير | إعادة تنفيذ قواعد الخطورة أو الاتصال المباشر بـWazuh |
| integrations | موصل Wazuh وتحويل الحقول وبيانات المكونات واستيراد أدلة الاختبار | تخزين التطبيق أو تحديد القرار النهائي أو تعطيل أجهزة دون موافقة |
| evaluation | بيانات اصطناعية موسومة، اختبارات السيناريوهات، حساب المقاييس | تغيير قواعد المحرك لتلائم نتائج الاختبار دون توثيق |
| contracts | التعريف المشترك للتنبيه والحادث وواجهات التبادل | أسرار الاتصال أو بيانات حوادث حقيقية |

## التقنيات والقرارات الأولية

- backend: Python + FastAPI وSQLite للنسخة المحلية الصغيرة؛ الترحيلات والاعتماديات تضبط عند التنفيذ وفق [ADR 0001](adr/0001-unified-platform.md).
- engine، integrations، evaluation: Python. يبدأ engine بوحدة قابلة للاستدعاء من backend لتجنب تعقيد خدمات مستقلة مبكراً.
- frontend: HTML + CSS + JavaScript دون إطار واجهات. يعتمد على API وعينات متفق عليها في contracts، ويستخدم fetch() لتبادل JSON.
- تعتمد المكونات على عقود مشتركة بدلاً من استيراد تفاصيل بعضها الداخلية.
- يحدد الفريق إصدار Python ويثبت اعتمادياته عند تجهيز التشغيل. لا تحتاج الواجهة في النسخة الأولى Node أو خطوة بناء.
- التلخيص الذكي توسع بعد استقرار المحرك؛ لا يقرر وحده أولوية الحادث أو ينفذ استجابة.
- التعلم الآلي للتقييم السياقي مختلف عن التلخيص اللغوي. مكان خصائصه والتنبؤ وسياسة الدمج engine/، ومجموعات التقييم والمقارنات داخل evaluation/. تفاصيل القواعد وسياسة الانتقال في [ENGINE_RULES.md](ENGINE_RULES.md).

## تقديم الواجهة وتبادل البيانات

- يقدم FastAPI صفحات HTML وملفات CSS وJavaScript مع مسارات API تحت `/api/` من نفس البروتوكول والعنوان والمنفذ في النسخة الأولى.
- تتبادل عمليات التنبيهات والحوادث البيانات بصيغة JSON؛ تستخدم الطلبات ذات جسم JSON ترويسة `Content-Type: application/json`.
- التنقل بين الصفحات يتم بروابط عادية، بينما تحدث الجداول والتفاصيل عبر fetch() دون إعادة تحميل الصفحة كلها عند كل تحديث بيانات.
- يفصل frontend/js/api.js الاتصال بالخادم عن ملفات العرض. تتحقق الواجهة من حالة الاستجابة وتعرض حالات التحميل والفراغ والخطأ.
- توثق استجابات النجاح والأخطاء والعينات في contracts عند تنفيذ API؛ أشكال الحقول ومسارات العمليات التفصيلية لم تعتمد بعد.
- تنزيل ملفات التقارير يمكن أن يعيد ملفاً مباشرة؛ اتفاق JSON يخص تبادل البيانات ولا يلزم تحويل الملفات إلى JSON.

## وظائف النسخة الأولى

أول مسار مصادقة بفشل ثم نجاح، وأدلة ناقصة وتغطية محددة، ثم سيناريو كشف للنشاط اللاحق بمسارين وخريطة يدوية وعطل مشترك وتحسين واحد مختبر. R01/R02 أساس البداية، وبقية القواعد والسيناريوهات تتبع بوابات النطاق.

النطاق التفصيلي ومعايير القبول في [شرح المشروع](PROJECT_SCOPE.md) و[المتطلبات](REQUIREMENTS.md). تشمل اختبارات المصادقة أيضاً جهازاً جديداً ونشاطاً مشروعاً وBrute Force وPassword Spraying، مع بيانات ناقصة وحالات متداخلة.

## تقسيم داخلي مستهدف (ينشأ عند التنفيذ)

```text
engine/
  triage/          # تجميع وربط وقواعد وأولوية أولية
  investigation/  # checklist وتفسير وإعادة تقييم
  resilience/     # تبعيات ومسارات ومجموعات فشل وتوصيات
  ml/             # لاحقاً بعد نجاح الأساس
backend/          # API وتخزين وتنسيق وتسليم نتائج
integrations/     # موصل وتحويل وقراءة حالة واستيراد دليل
evaluation/       # سيناريوهات ووسوم واختبارات فشل ومقارنات
frontend/         # HTML/CSS/JavaScript
contracts/        # عقود مشتركة لكل المكونات
```

التقييم يملك الحقيقة المرجعية وتنفيذ تجربة المختبر بإشراف مسؤولها؛ engine يتلقى تمثيل الاختبار ولا يتصل بالأجهزة. backend يحتفظ بنسخ الخريطة والقواعد ونتائج الاختبار وسجل التدقيق، ولا يدفن منطق التحليل داخل routes. صفحة الواجهة تعرض ما هو توقع وما هو مختبر.

## تعديل الهيكلية

يفتح المقترح كمهمة مع السبب والأجزاء المتأثرة، وتُراجع هذه الوثيقة وعقود البيانات ضمن طلب الدمج نفسه. لا يبدأ تغيير مؤثر على عدة أجزاء قبل التنسيق مع مسؤوليها.
